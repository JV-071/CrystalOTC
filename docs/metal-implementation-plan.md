## Phase map and sequencing

```
P0 Baselines [done] ──► P2 Renderer boundary [gate met 2026-08-21] ──► P3 GL on RenderFrame [gate met 2026-08-21] ──► P4 Metal foundation [gate met 2026-08-21] ──► P5 Targets & composition [gate met 2026-08-21] ──► P6 Materials [landed 2026-08-21; measured locally, CI unproven] ──► P7 Hardening
                            ▲
P1 Cocoa platform [done] ───┘  (P1 and P2 both landed 2026-08-20 — sequentially in the end, though neither blocked the other; P4 needs P1+P3 done)
```

- **P1 ∥ P2:** the Cocoa window needs no renderer work and the boundary needs no macOS.
- **P3 before P4** is the plan's central risk control: the frame model must reproduce today's GL output pixel-for-pixel *on the existing platforms* before any Metal code interprets it (companion doc, Phase 3 rationale).
- P5 and P6 have a partial overlap opportunity: built-in materials land in P4; the shader toolchain (P6) can start as soon as P2 freezes `MaterialParams` — **which it did on 2026-08-20 (`render/materialparams.h`, std140, `sizeof == 80`, offsets static_asserted), so P6 toolchain work was unblocked from that date — and was delivered 2026-08-21, the frozen block travelling per packet to both backends**.

Scope calibration from the companion doc's table: this is the "Backend-neutral frame architecture plus OpenGL migration" (Large) plus "Direct Metal with full OpenGL visual parity" (Very large), with P1 "Medium" and P7 "Medium after rendering works". The existing Vulkan renderer (~5,800 lines) and the Win32/X11 windows (~1,100–1,300 lines each) remain the best available size anchors.

## Phase 1 — Native macOS platform layer (parallel track)

**Goal:** a native `.app` that opens a Cocoa window, processes input, resizes, and presents a clear color through a bare `CAMetalLayer` — no renderer architecture involved.

**Delivered 2026-08-20** behind the opt-in CMake option `TOGGLE_COCOA_WINDOW` (`src/CMakeLists.txt:16`), **default OFF**: XQuartz stays the default macOS build because it is the OpenGL reference vehicle every Phase 0 baseline is captured through, and the Cocoa window deliberately provides no GL context. The two platform layers are mutually exclusive and never linked together (`src/CMakeLists.txt:214-232`, `:1057-1073`), and the Cocoa build links Apple's `OpenGL.framework` rather than XQuartz GL (`:312`).

The macOS milestone is complete when: the `.app` runs the full 16-scene validation matrix locally, with Metal output matching the OpenGL backend's output for the same scenes — both driven from the same `RenderFrame` — within the manifest's `renderBackendTolerance` policy (the `renderBackendComparable` escape hatch was emptied by Phase 6 and no scene uses it) (there is no frozen macOS reference set, and since 2026-08-21 there is no longer a need for one); the CI-capturable subset (11 scenes, 8 of them gated), the legacy-versus-frame parity sweep over all 11 (`tools/compare_render_paths.sh`, added 2026-08-21) and the golden-frame suite are required CI, with the macOS matrix (`tools/run_macos_matrix.sh`, added 2026-08-21 — the legacy-versus-frame sweep, the OpenGL-versus-Metal sweep over the comparable offline scenes via `tools/compare_render_backends.sh`, and the online scenes against their own noise floors via `tools/compare_online_backends.sh`) run **locally** before a macOS release rather than in CI — it needs one Cocoa binary and one XQuartz binary at once, and no hosted runner can provide the second **— or, while branch protection stays deliberately absent (owner decision 2026-08-20), green on every push to `main` with a loud failure; "required" resumes meaning a protected check when a second contributor appears** — the rest of the matrix cannot be required, because three scenes need `data/things/*`, one needs a window manager and four need the fixture server; the llvmpipe CI job, green since 2026-08-20 (one red run since — `32433421802`, the `bf4458b` state-stack segfault, green again from `32436668903`), continues to prove GL-on-`RenderFrame` parity **once its `shader-matrix` reference is reseeded after the `rain.frag` fix in `19e29e3`, which moved OpenGL output by 2,032 px on that scene; until then the job is expected red there, and it has not yet run on any Phase 6 commit** (standing in for Windows/Linux runtime validation); Windows, Linux and macOS CI are green — Windows compile-gated and unit-testing with the Vulkan feeder behaviour-unchanged by construction, Linux compile-gated, unit-testing and holding the llvmpipe pixel gate, macOS building, unit-testing, bundle-checking, smoke-launching the Cocoa `.app` — asserting the resolved renderer and the CPU-atlas configuration while it does, and attempting the image matrix non-gating — as a required job **(subject to the same branch-protection qualifier above)**; and the shader toolchain rejects untranslatable GLSL — at build time wherever glslang, spirv-cross and Python3 are present (`check_metal_shaders`), unconditionally in CI, and in both cases also when a shipped `.frag` is neither translated nor excluded-with-a-reason.
