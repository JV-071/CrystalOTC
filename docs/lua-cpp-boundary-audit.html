The Lua Waterline

Where the C++/Lua line sits in this client, where it's drawn wrong, and — mostly — where it's already right. Most of the 236k lines of Lua should stay exactly where they are.

One fact reframes the whole question

There is no Lua on the render path. Searching modules/ and mods/ for onDraw or onRender handlers returns nothing, and uiwidget.cpp never calls into Lua during draw. The only per-frame Lua entry point in the entire client is g_app.onFps, once a second.

So Lua costs you in exactly three places: timer ticks, input events, and the ~205 network-driven callLuaField crossings out of game.cpp and protocolgameparse.cpp. That kills the usual argument for a bulk migration — a 26,000-line module that only runs when someone opens a window is not costing you anything, no matter how large it looks in a line count.

The highest-payoff C++ work in this repo is not in modules/. It's in luaengine/ — making the crossings you already make cheaper.

Move to C++

Engine mechanics that leaked upward

Four of these are infrastructure, not game content — and two of them sit under every Lua call you make, so fixing them speeds up code you never touch.

Every property access builds a std::string

src/framework/luaengine/luainterface.cpp:214, :262

luaObjectGetEvent is the __index metamethod for every bound class — every widget:getHeight(), every creature:getPosition(), every field read in 236k lines of Lua lands here. It does lua->getField("get_" + key), concatenating a fresh std::string per access. The write path does the same with "set_" + key. Names like "get_setMarginTop" blow past small-string optimisation and heap-allocate.

Worse, method calls — the common case by far — pay for two failed prefixed lookups before the method table is even consulted: metatable → fieldmethods → get_+key → luaGetField → metatable → methods → key.

Fix: precompute the get_/set_ prefixed keys once at registerClass time, or intern them per class. No Lua-visible change — but the lookup order must be preserved exactly or styles that define both a field and a getter will silently flip behaviour.

every crossinghigh payoffmedium effort

The event gate is missing on the overload that needs it most

src/framework/luaengine/luaobject.h:207-216 vs :218-234

The void overload of callLuaField memoises "this object has no handler for this field" in m_events and returns early. The R-returning overload has no such check — and that's the one every input event uses: onMouseMove, onKeyDown, onKeyPress, onMousePress, onDragMove, onMouseWheel.

uimanager.cpp:178-180 walks the whole widget chain under the cursor calling onMouseMove on each. For a widget with no handler you still pay asLuaObject() (shared_from_this plus a try/catch frame), pushObject, a registry lookup, getField, a nil test and two pops. The game interface is typically 5–15 widgets deep. Almost none of them have a handler.

Fix: apply the same m_events gate to the templated overload. Note the existing cache is never invalidated when a handler is set to nil — that staleness is already present and you'd be inheriting it, so decide deliberately.

Split it

Policy stays up, primitives go down

This is the most useful part of the answer. The automation and list code shouldn't move to C++ — the rules are exactly what users edit. What should move are the scan-and-filter primitives those rules call, so one crossing replaces hundreds.

Spectator scans, one getter at a time

modules/game_helper/helper_shooter.lua:654-688 · helper_heal_friend.lua:850 · helper_autoparty.lua:176

g_map.getSpectators returns a fresh Lua table of userdata, then Lua loops it calling isMonster, isDead, isNpc, getPosition, isSightClear — a boundary crossing each, every one paying the "get_"+key concat above. Three helper modules each run their own scan on the same 50 ms tick. helper_autoparty.lua:176 calls getSpectators inside a four-iteration loop.

battle.lua:1252 shows the same shape in the UI: doCreatureFitFilters does ~15 crossings per creature, calls getLocalPlayer() twice per creature, and allocates two closures per iteration from the inline (function() … end)() blocks at lines 1293 and 1298.

Boundary: g_map.queryCreatures(centerPos, opts) → flat array with opts = {minDist, maxDist, sameFloorOnly, requireSightClear, kind, excludeIds, withPositions}, returning plain records {id, x, y, z, hpPercent, distance}. One crossing, no per-creature userdata. Every threshold, priority and rule stays in Lua.

Area-of-effect tile search in Lua

modules/game_helper/helper_shooter.lua:1259-1329

findBestTileForRune nests for each creature → for dy → for dx, and each candidate allocates a {x,y,z} table plus seen column tables, then calls g_map.isSightClear and countAttackableCreatures — which loops the area offsets and calls isSightClear again per occupied tile. It's an O(creatures × area²) spatial search running in the scripting layer.

Boundary: g_map.findBestAreaTile(fromPos, areaOffsets, opts) → {pos, hits}, returning the top N so the Lua rule keeps the final say. Lua still owns the spell's area shape and direction rotation, which it already caches.

Smaller splits worth doing

  • Point/Size marshalling — luavaluecasts.cpp:166 allocates a fresh 2-slot Lua table per coordinate. Two per widget per mouse-move, over a ~10-deep cursor chain, at 125 Hz polling. Adding scalar accessors (g_window.getMouseX/getMouseY) is the cheap half.
  • UIWidget::getChildren() returns m_children by value (uiwidget.h:734) — a vector copy plus a refcount bump per child, then a Lua table. uiminiwindow.lua calls it four times per mouse-move while dragging. Expose getChildCount()/getChildByIndex().
  • Key combo descriptors — keyboard.lua rebuilds 2–4 strings per key event, ~33 Hz per held key, for a pure function of two small integers. Memoise in Lua or expose g_window.getKeyComboDesc.
  • Mini-window container layout — uiminiwindowcontainer.lua's fitAll is constraint-based vertical space distribution with per-child min/max. That's engine layout, and there is no C++ UIScrollBar or container layout to fall back on.
  • Cyclopedia item index — items.lua marshals the whole item catalogue one userdata at a time and sorts in Lua. The 300-per-frame chunking is in-repo evidence the synchronous version stalled. ThingTypeManager already holds every field it needs.
Keep in Lua

Roughly 200,000 lines, correctly placed

Listing these explicitly so a line-count heuristic doesn't sweep them up later. Several are the obvious migration targets that turn out not to be.

The protocol boundary is already right

src/client/protocolgameparse.cpp → modules/gamelib/protocolgame.lua

Lua does no wire parsing anywhere. Every byte is read by bounds-checked C++ and Lua only ever sees typed arguments. This is the security-sensitive path and it's in the right language — there is nothing to pull out and no argument for pushing more in.

One structural hazard worth knowing: because a Lua handler can consume bytes and return true, a handler that under-reads leaves the stream mid-opcode. That's a design property, not a bug in any one file.

already correct

There is no pathfinding in Lua to migrate

modules/game_walk/walk.lua

The single most obvious C++ candidate isn't one. Path search is already entirely in Map::findPath; Lua only supplies a destination. What remains runs per keystroke and does 1–3 g_map.getTile calls — bounded by human finger speed.

The logic it does hold — smart-walk diagonal preference, the always-walk rules — is exactly the server-specific behaviour owners tune.

already correct

Big files that are just data

gamelib/spells.lua · gamelib/wheeldestiny.lua · game_cyclopedia/** · data/locales/**

spells.lua is ~94% static table. wheeldestiny.lua is 100% content expressed as builder calls, evaluated once at load — no hidden tick loop. game_cyclopedia is 26,029 lines of content tables and open-a-window UI that sits idle until a player opens a tab.

The scariest-looking accessors — getSpellByIcon and friends doing nested pairs scans — traverse about 160 entries on a cooldown packet. Sub-microsecond. Moving any of this to C++ would freeze taxonomies that differ per server and buy nothing anyone can perceive.

content, not engine

Automation rules — the policy half

modules/game_helper/**

Spell ids, rune ids, race priorities, HP thresholds, vocation gating, stance ordering: all server-specific content that users edit live through the UI and expect to hot-reload. The schema visibly still churns (harmony, forceCast, useTo=bestTile read as recent additions) — freezing it in C++ now would be premature.

What these modules need isn't migration, it's memoisation. The healer rebuilds and sorts its entry list three times per 50 ms tick for an ordering that only changes when the user edits config. helper_target rebuilds a priority index twice per creature per tick. helper_heal_friend does ~480 string allocations per tick normalising names that are constant. All three fixes are pure Lua, and this codebase already knows the pattern — helper_conditions.lua:783 and helper_tools.lua:1720 both cache correctly.

The model of what the split should look like

modules/game_creatureinformation/ · modules/game_attachedeffects/

Per-frame per-creature drawing was already moved into C++ and the Lua version demoted to a warned-about fallback. game_attachedeffects is pure declarative config — effect id to sprite, offset, duration — over a C++ effect system that does all the per-frame work.

This is the direction of travel the rest of the recommendations follow: draw and scan in C++, decide in Lua.

reference pattern

Also correctly placed

  • corelib/keybind.lua (1,187 lines) — it only binds. Key dispatch is not happening in Lua per keypress; callbacks fire once per press.
  • modulelib/controller.lua — not a hot dispatch layer and adds zero crossings per event. Handlers are installed on the widget and invoked directly by C++. Lifecycle glue that mods extend.
  • client_options/** (12,341 lines) — config plumbing. setOption runs on user interaction only. The option set is precisely what server owners extend.
  • gamelib/creature_list.lua — the spatial query stays in C++ where it belongs; this is per-event UI policy over it. Not a re-derived spectator query.
  • gamelib/player.lua food regen — a 5,000 ms cycle doing two nil-guarded calls and a subtraction. It also stores a timestamp and derives on demand rather than decrementing per tick, which is the robust shape already.
  • gamelib/engine_compat.lua — install is self-disabling, so each shim evaporates when the real binding lands. Zero runtime cost. Worth auditing the entries that fabricate data, not the mechanism.
  • The big mods — proficiency.lua (3,655 L) and t_market.lua (3,625 L) have no recurring timer and no per-frame handler between them.
  • game_interface sidebar and game_console — already coalesce layout into one addEvent per frame, cap the console at 100 recycled labels, and batch with disableUpdateTemporarily.
Delete

Duplicated work, in both directions

The clearest wins in the whole audit, because nothing has to be designed — one of the two copies just goes away.

Two complete HTML/CSS engines, and the C++ one is unreachable

src/framework/html/** (5,075 L, compiled & bound) vs modules/modulelib/htmlcssparser/** (1,575 L, live)

g_html is registered at luafunctions.cpp:482-487 with load, createWidgetFromHTML, addGlobalStyle and getRootWidget. It has zero call sites across every .lua file in the repo. Meanwhile Controller:loadHtml routes through the pure-Lua HtmlParser, and that's what game_prey_html, game_npctrader_html, game_blessing and game_htmlsample actually use.

The Lua loader also implements reactive attribute binding by polling: htmlloader.lua:3 sets WATCH_CYCLE_CHECK_MS = 50 and re-evaluates the watch list 20 times a second.

Decide which one lives. Parsing is infrastructure and malformed-input handling matters, so the C++ engine is the better home — but it has never been exercised, so treat "switch to it" as a real project, not a flag flip. What isn't defensible is carrying both.

Cooldown sweeps that C++ already animates

modules/game_actionbar/game_actionbar.lua:8045-8072

updateCooldown re-schedules itself every 100 ms per active cooldown: one closure and one ScheduledEvent per tick, 2–4 crossings, and a string.format allocating a fresh string each time. A spell burst across a full nine-bar layout puts dozens of these chains in flight at once.

UIProgressRect already does this natively — uiprogressrect.cpp's start() tracks m_startTime, m_duration and m_timeElapsed and fires onProgressFinish — and setDuration, start, stop and showTime are all bound at luafunctions.cpp:1334-1342.

Fix: call setDuration(ms) + start() and handle onProgressFinish. Delete the ticker.

Dead debug machinery that every event still pays for

modules/corelib/globals.lua:8-13, :132-160

The wrappers capture g_dispatcher.setNextEventSource, hasNextEventSource and setActiveEventSource. None of those exist anywhere in src/ — all three resolve to nil, so the ~120 lines of debug.getinfo stack-walking they feed is unreachable.

But _wrapEventCallback still runs unconditionally: it allocates a new closure per scheduled event and wraps every fire in a pcall frame, purely to service hooks that aren't there. There are ~473 addEvent/scheduleEvent/cycleEvent call sites.

Fix: either implement the C++ side or delete the wrappers and restore the native functions. Right now you have the cost without the feature.

A guard that never fires

modules/corelib/ui/tooltip.lua:274, :301

local function moveToolTip(first) opens with if not first and (not toolTipLabel:isVisible() …) then return end. Connected as onMouseMove, the signal passes (widget, mousePos, mouseMoved) — so first receives the widget, is always truthy, and the early-out is dead. Straightforward removals

  • corelib/struct.lua — 203 lines of pure-Lua binary pack/unpack with zero call sites, parsed at every client start. Worse than useless: it sits beside the code that handles binary data and invites someone to use it for protocol work that must stay in C++.
  • battle.lua duplicating creature_list.lua — ~800 lines of parallel list machinery, both loaded every session. Guarantees drift: a sort-stability fix applied to one won't reach the other, and the battle list and party list will disagree.
  • Two copies of canBeSeen — creature_list.lua:74 and battle.lua:2315, the latter a bare global. Whichever loads last wins if they ever diverge. Nearby, table.remove(queue, 1) in a drain loop is an accidental O(n²) inside batching that exists to avoid a frame spike.
  • Container slot decorations — count and duration rendering in containers.lua duplicates uiitem.cpp down to the format strings, and adds ~5 extra widgets per slot (a 36-slot backpack becomes ~250 widgets).
  • Empty tombstones — mods/game_bot, game_walker, game_huntfinder, mods/game_helper and modules/game_analyser contain no Lua at all. They shadow the real modules (modules/game_helper, modules/game_analysers) and mislead anyone grepping.
Sequence

If you do one thing, then the next

Ordered by payoff per unit of risk. The first three are hours, not weeks, and two of them speed up code you never touch.

  1. Fix the four cheap defects

    The tooltip guard, the dead event-source wrappers, struct.lua, and the empty mod stubs. No design decisions, no API surface, immediately measurable.

    hours · zero risk
  2. Gate the templated callLuaField

    One overload in luaobject.h. Every widget in every cursor chain stops paying for handlers that don't exist. Decide the nil-invalidation question deliberately while you're in there.

    small · touches every input event
  3. Kill the "get_" + key concatenation

    Precompute prefixed keys at registerClass time. This is the one change that makes all 236k lines of Lua faster without editing any of it. Preserve lookup order exactly.

    medium · highest leverage in the repo
  4. Retire the two duplicated animations

    Actionbar cooldowns onto UIProgressRect::start(), the proficiency ring onto UIProgressArc. Both C++ widgets exist and are already bound — this is deletion, not migration.

    small · high payoff
  5. Add g_map.queryCreatures

    One flat-array spectator query with filter options. Then port helper_shooter, helper_heal_friend, helper_autoparty and battle.lua onto it one at a time. Rules stay in Lua throughout.

    medium · unblocks four call sites
  6. Memoise inside game_helper

    Cache the healer's sorted lists, the target priority index, and the normalised party names. Pure Lua, no boundary work, and the codebase already has the pattern in helper_conditions and helper_tools.

    small · no C++ needed
  7. Decide the HTML engine question

    5,075 lines of C++ or 1,575 lines of Lua — pick one and delete the other. The C++ path is the better home for a parser but has never been exercised, so scope it as a project.

    large · mostly a decision
  8. Then the big spatial ones

    Minimap marker layer and the battle-list sorted query. Real design work, real payoff, but only worth starting once the cheap leverage above is banked.

    large

How this was checked

Four agents read disjoint slices of the Lua surface — corelib and the input path, gamelib and protocol, the game_helper automation stack, and the large UI modules plus the binding surface. Every finding above was then re-verified directly against the source: the string concatenation in luainterface.cpp, the missing gate in luaobject.h, the 184 pixel widgets, the UIProgressRect and UIProgressArc bindings, the zero g_html call sites, the marker count in markers.json, the dead dispatcher hooks, and the tooltip signature.

Two claims that came back were corrected in the process. The game_helper tick allocating a four-field table 20 times a second is not a migration argument — that's negligible on LuaJIT, and it's listed under memoisation instead. And globals.lua's wrappers aren't built on missing dispatcher functions; addEvent, scheduleEvent and cycleEvent are all bound. It's the three event-source debug hooks that don't exist.

Also worth knowing while you weigh any of this: GarbageCollection::poll runs a full LUA_GCCOLLECT — twice, back to back — every 60 seconds, with the source comment noting it "costs a few ms". That stall scales with the size of the Lua heap, which is the one place where total Lua volume, rather than Lua hotness, actually shows up.
